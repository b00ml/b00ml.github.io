v1 上线以后我自己用得不多。不是因为功能少，是因为**每次让它动一下笔记，都要先点一次同意**。整理一篇笔记要点三次，一次对话里有五个工具调用就弹五个框。弹到第三个我就开始盲点「允许」——那一刻审批已经不是保护，是把注意力从内容上挪走的噪音。

v2 的重构只有一句话：**把「事前逐次同意」换成「事后一键撤销」，只在撤销不了的地方保留事前确认。**

## 删掉逐次写审批，不是放松，是换抵押物

v1 的假设是「写坏了就回不去了」，所以每次写之前都要拦一下。这个假设在 Git 面前不成立：Vault 是一个 Git 仓库，一次操作产生的所有写入可以合成一个提交，撤销就是 `git revert`。

于是 v2 的规则变成：

- **普通问答默认只读。** 用户没说要改，Agent 就不改。
- **用户明确要求写入后，在授权范围内直接执行。** 不再逐次弹框。
- **每一次操作一个快照。** 一轮对话、一次 Skill 执行、一次插件请求、一次定时任务运行，期间的多次写入**合并成一条**提交，提交信息是 `ark(<source>): <操作> <路径>`。历史面板按来源筛选，一键撤销单条或一段。
- **撤销不改写历史。** 用 `git revert` 生成新提交，所以撤销本身也能再撤销。

单位从「一次工具调用」变成「一次操作」，是这次重构里最关键的一处。按调用记快照会得到一堆「改了同一篇笔记三次」的碎片，人在历史面板里根本认不出哪一条是「我刚才那次整理」；按操作记，一条提交就对应一次意图。

有三个地方必须诚实：**快照不是事务**。中途失败时已经发生的写入会收束成一个可撤销的快照并明确报告，但不宣称「要么全成要么全败」。**外部宿主的快照边界更粗**——Core 看不到它的操作边界，所以外部宿主每调一次写工具就产生一个快照，比自家 Agent 更碎。**用户手改不会自动提交**，只在 Ark 下次写同一个文件之前保存修改前的版本。

## 只给撤销不了的动作留事前确认

有一条边界 Git 跨不过去：**Vault 以外的东西**。邮件发出去就收不回，消息推出去就删不掉，对外发布同理。所以事前确认没有取消，只是收窄到这一类：

| 动作 | 事前确认？ | 谁负责 |
| --- | --- | --- |
| Vault 内写入（整理笔记、改 frontmatter、移动文件） | 否，直接执行 + 快照 | Ark Core |
| 采集类工具（取字幕、抓文章） | 否，只读，放在免确认名单 | Ark Core |
| 发邮件 / 发消息 / 对外发布 | **是** | ark-agent 在回环里暂停，SSE 推 `ark.pending_action`，用户批准才执行，拒绝也作为工具结果回填给模型 |
| 定时任务里的外部动作 | 启用时一次性授权，运行时不逐次问 | ark-agent 调度器 |
| 外部宿主调用的外部动作 | 由宿主自己的工具审批负责 | 宿主 |

一个细节值得单独说：**MCP 的 `readOnlyHint` / `destructiveHint` 这些注解不用来判断安全性。** 规范里写明了它们只是 server 自报的提示，不能据此做安全决定。所以默认全部确认，只在 `ark.toml` 的 `auto_approve` 名单里按 `mcp__<server>__<tool>` 通配显式放行——只读的采集工具才在里面。

## 五套账本并成一份真源

v1 分开记五套账：会话、任务阶段、外部副作用、记忆生命周期、索引版本。当时的想法是「多一张账本，出问题时能定位到哪一段」。这个判断本身没错，错在**账本的存放方式**：五套独立状态，就有五处可能和真实文件不一致，就有五套迁移和五套对账。

v2 的做法是把「状态」全部落回 Markdown 与 frontmatter，并接受一条更弱的承诺：**能从不一致里恢复，而不是保证不会不一致。**

| v1 | v2 | 为什么可以砍 |
| --- | --- | --- |
| 会话账本 + 任务阶段账本 | 话题线程的 Live State：`ark/threads/<slug>.md`，五段正文 + 五个 frontmatter 字段 | 会话本身不需要记账，需要接着想的是「假设 / 未决 / 待定 / 下一步 / 已确认」这五段 |
| 外部副作用账本（planned → leased → executing → verifying → succeeded，含 unknown 恢复屏障） | 不建账本：外部写动作在 Agent 回环里暂停等确认，结果以外部系统自己的记录为准（邮箱的「已发送」） | 一个只有一次确认的外部动作，不值得一套状态机；真正需要的是确认卡与拒绝回填 |
| 记忆生命周期账本（candidate → 人审 → active → 各分支） | 一条记忆一个 Markdown 文件，`status` 只有 `inferred` / `confirmed` 两值，`feedback.jsonl` 追加确认、驳回、修改、降级记录 | 状态越多，越难回答「这条现在到底算不算数」；两值 + 可追查的通道记录已经够用 |
| 索引版本账本 | 索引是派生物：`<vault>/.ark/index.db`，按文件修改时间增量更新，删掉能完整重建 | 派生物不需要自己的账，它只需要能重建 |
| CAS 写入账本（内容 hash 比对 + 只写原子替换） | 保留路径守卫与原子替换，但冲突不再用自建 CAS 判定：并发冲突交给 `rev`/`base_rev` 与 Git | 同一件事不要有两套实现 |

砍完之后，Vault 里多了什么？只有三样：`ark/threads/`、`ark/memory/`、`ark/feedback.jsonl`。**删掉 `.ark/` 全部重建**，笔记一条不丢；删掉 `ark/` 状态目录，笔记还在，只是记忆与断点回到空——这是明确的代价，写在设计里而不是藏起来。

## 减法也是删依赖

同一轮里还删了几样不在标题里、但同样占地方的东西：

- **不写 QQ 网关**：AstrBot 直接连 `/mcp`，网关那层由它负责。
- **不自写邮件收发**：优先用现成的 IMAP/SMTP MCP server。
- **不搬 v1 的插件面板**：feeds、daily、moc、caselib、cards、skins 这些硬写在主插件里、删不掉的子界面，一个都不进 v2；需要界面和定时运行的功能改成 Ark 插件，能单独停用。
- **不迁 v1 的记忆数据**：新版状态从空开始，继续用既有笔记。
- **不引 Agent 框架**：先写一个简单回环，模型调用统一走 LiteLLM。

判断标准只有一条：**换一个更强的模型进来，我这边要改多少行。** 改得越少，越说明这一层是我的资产。

## 减法之后剩下什么

删完之后系统小了一圈，但下面这些一条没少——它们才是记得住的部分：

- 笔记是真源，Markdown 是唯一真相，索引和缓存删了能重建。
- 授权范围内直接写，每次操作可撤销。
- 推断和结论在数据上分开，`inferred` 永远带标记。
- 能力经 MCP 暴露，Skill 写成文件，自家 Agent 和外部宿主用同一套，没有内部捷径。
- 凭据只放 `.env`，不进仓库、不进 Vault、不进日志。

「做减法」在 v2 里不是一句态度，是一条可执行的设计规则：**每加一个状态、一个开关、一个配置项，都要有当下的真实需求；用不上的就删。** v1 的五套账本就是这条规则的反面教材——它们都是「万一以后要用」的产物。
