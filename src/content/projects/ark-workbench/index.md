## 它能完整办成的一件事

把一个 B 站视频或一篇公众号文章丢进去，出来一条带来源、带结论、带反例、带有效期的结构化记录，写进 Vault；之后按问题检索，能把它取回来引用，也能追到这条结论是从哪一段原话里得出的。

中间的事它自己处理：字幕下载失败就降级到 Whisper 转写，结构化结果过二次校验，写 Vault 只走受控路径，索引跟着刷新。我只需要在「这条记录要不要进长期记忆」这一步点一次头。

这条链路我按「三个月前的我做的判断，今天还能不能复现」来验收——它不是能存多少，而是能不能被再拿出来用。

## 我为什么把它做成这样

我不做通用助手。判断某个能力该不该自己做，标准只有一条：换一个更强的模型进来，我这边要改多少行。改得越少，越说明这一层是我的资产，而不是模型的临时参数。

按这条标准，有三个决定：

**只做「我自己的上下文」这一层。** 一旦它什么都能答，它就变成又一个会被模型升级冲掉的东西。它只回答关于我的问题：我读过什么、当时怎么判断、后来有没有被推翻。

**状态不合成一个。** 会话、任务阶段、外部副作用、记忆生命周期、索引版本是五套账本，各记各的。「任务成功」推不出「工具都成功了」，「工具返回成功」也推不出「外部系统已经完成」。多一张账本，换的是出问题时能定位到哪一段。

**写入只留一个口。** raw/ 只读，templates/、.obsidian/、.git/ 直接拒写；写入走临时文件加原子替换，冲突检测用内容 hash 做 CAS。独立 CLI 拿不到统一写入层时，返回里明确写 governed=false，而不是假装治理已经完成。

## 四段链路

采集、编译回读、产出各占一段，运行时横在下面托着这三段。四段各有自己的失败码，不合并成一个「处理失败」。

- [从一条链接到一条可引用的记录](/projects/ark-workbench/pipeline)：三条入口、字幕三层降级、缓存与去重、写入守卫。
- [一次对话在运行时里经过什么](/projects/ark-workbench/runtime)：请求准入、上下文清单、工具权限、审批、外部副作用账本。
- [一条事实要过几道门才允许被读出来](/projects/ark-workbench/memory)：模型提候选、人审激活、按 purpose 读门禁、失效按序传播。
- [我怎么证明它真的能跑](/projects/ark-workbench/evidence)：七层证据、候选身份绑定、能下和不能下的结论。

## 做到什么程度

四段链路都能跑通，运行时五段治理齐备，写入有唯一受控路径。记忆层是完整的：模型只能提候选，激活要过人审，读取要报 purpose，失效按 suppression → Markdown → RAG → session range → outbox 的顺序传播。旧库迁移做完了：155 个文件、563 条记录，带 manifest、逐文件 hash 和 CAS 回滚。

内容入口现在是四个：B 站、文章、邮件，加上手工收录的 Coding Agent 复盘。收录的是我选定的记录，来源、决策理由、验证和失败尝试落在 Markdown 真源上；Agent 端只拿到一个只读查询工具，不自动收集我的会话。

入口还多了一个 QQ。本人私聊和每个白名单群各接一个受限的 Serve 实例：私聊默认纯聊天，群 @ 走只读知识检索——目录即授权，引用必须来自本轮证据并附逐字摘录，证据不足就明说。消息有独立的事件账本：确认成功才记已发送，重启不重放。这条线十月下旬通过了本人私聊的真实验收（真实 QQ、真实付费调用四问全对），群聊和跨成员还没验，费用先手动控制。

评测这块我按七层记证据：候选必须绑上 candidate_id、git commit、build sha256、任务集 hash 和源报告 SHA-256，才算一次可以横向比较的读数。

## 适用范围

它解决的是个人上下文这一层，单人、本机 Vault、自己写的笔记。团队协作、多人权限、云端同步不在范围内——那是另一种产品，加进来会把这条链路撑散。QQ 那个入口看着像多人，其实还是单操作者：谁能问、能读到什么，由本机白名单和授权目录决定。
