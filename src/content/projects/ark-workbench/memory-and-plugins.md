长期记忆最危险的不是记错，是**记错了却长得像对的**。模型顺手把一句猜测写成「用户偏好先看结论」，三个月后它和用户亲口说过的话混在同一个列表里，谁也分不出来。

Ark 的解法是把「谁说的」变成数据字段，而不是靠措辞猜。

## 两种状态，只有一个入口

记忆条目的 `status` 只有两个值：

| 状态 | 谁能写 | 读出来长什么样 | 进常驻层吗 |
| --- | --- | --- | --- |
| `inferred` | `remember` 工具、记忆抽取、模型提出的修订候选 | 文本前加 `[推测，未确认]` | **永远不进** |
| `confirmed` | 只能经 `confirm` | 原样 | 进（在 2k 预算内） |

关键在**没有直接写 `confirmed` 的参数**。`remember` 的签名里根本没有这个开关，模型再怎么想也写不进去；记忆抽取每次跑完，落盘的一律是 `inferred`，哪怕抽取出来的条目附了引用也还是 `inferred`——引用只用于追溯，不能仅凭「原文里有这个子串」就升级状态。

`[推测，未确认]` 这个前缀也不是装饰。它出现在按需层召回的结果里，模型看到的是带标记的文本，人看到的也是。一条猜测在两种视角下都不会伪装成结论。

## 确认要留通道，也要能撤回

`confirm` 会做两件事：把条目转成 `confirmed`，并在 `feedback.jsonl` 里记下 `via` ——**是谁确认的**。`via` 为 `obsidian` 表示记忆面板里的点击；其他值是调用方自报的宿主名。

这里必须承认一个限度：Core 分辨不出 `confirm` 背后是不是用户本人，外部宿主的模型也可能自己调它。所以设计不靠拦截，靠**可追查、可撤回**：

- 每次确认、驳回、修改、降级都在 `feedback.jsonl` 追加一行：`{ts, id, action, via, before, after}`。
- 记忆面板可以按 `via` 筛选，**一键把某个宿主确认的条目批量降回 `inferred`**。一次误确认不需要一条一条手工回退。
- `ark-protocol` Skill 里写死了规矩：只有用户明确表态，或确认了展示给他的具体条目，才允许调 `confirm`。

`via` 是自报的，不做身份认证——这一点写在设计里，不假装它是权限系统。它的用途是**事后追查**：出了问题能回答「这条是谁写进来的」，然后一个按钮把那一路清零。

## 修订不覆盖，替换要经人

模型读着读着觉得某条 `confirmed` 该改写，怎么办？

- 它**不能**直接改。改写建议走 `remember` 的 `supersedes`，新条目是 `inferred` 候选，旧条目原样不动，继续被使用。
- 候选里写的替代关系**不自动生效**。只有用户接受展示出来的替换内容后，`confirm` 才在同一个快照里删掉被替代的旧文件。旧内容仍能在 Git 历史里找到，所以不需要「已废弃」这种状态。
- 用户自己明确要求改某条，走 `edit`：原地更新文本，前后文本与依据记进 `feedback.jsonl`。`edit` 的 `status` 只接受 `inferred`，用于把已确认条目降回推断——**降级是 `edit`，确认是 `confirm`**，两个方向不共用一个入口。

`forget` 的承诺也要说准：它停止把该条作为当前记忆使用并删除当前文件，**不承诺**删掉 Git 历史、`feedback.jsonl` 或已开启的会话归档里的副本。界面明确写这个范围，彻底清除所有历史副本不进 MVP。

## 防污染靠机制，不靠宣称号称

把上面这些合起来，其实是一道道闸门：

```
用户说过的话 ──► excerpt（只在内存里过一遍，不落盘）
                    │
                    ▼
              一次 LLM 抽取 ──► inferred（前缀 [推测，未确认]，不进常驻层）
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
   用户确认（confirm）        用户驳回/修改/降级
        │                        │
    confirmed + via          feedback.jsonl 追加一行
        │                        │
   进 2k 常驻层              仓库里的记忆面板可按 via 批量降级
```

设计文档里写的是「这是防止跨会话记忆污染的主要机制」，然后紧跟一句：**效果用指标衡量，不宣称「消除」污染。** 推断被驳回的比例只记录趋势，不设目标——设了目标就会有人为了达成目标去少写推断。

`excerpt` 那一环值得单独看：它是用户本人说过、可能跨话题有用的原话，**只作为抽取输入、只在内存里经过、不写磁盘**。所以「保存进度」和「抽取记忆」是两件独立的事——抽取模型没配、预算用完、调用失败，断点照样已保存，报告里分开写两行。

## 插件契约：数据只放 Vault Markdown

Ark 插件是第三种扩展类型，用在 MCP 和 Skill 表达不了的地方：要独立界面、要定时运行、要用 Ark 自身能力（上下文注入、预算内模型调用、通知）。

它有三部分，位置各不相同：

| 部分 | 在哪运行 | 做什么 |
| --- | --- | --- |
| 后端 | `ark serve` 进程内，Python，入口 `setup(ctx)` | 注册工具、定时任务、上下文提供者、给界面用的接口 |
| 界面 | ark-obsidian 里，TypeScript，入口 `setup(view_ctx)` | 注册侧栏视图、标签页、命令、设置页 |
| 数据 | Vault 里的 Markdown + frontmatter，放在 `<data_dir>/<name>/` | 和普通笔记一样能看、能搜、能撤销、能 forget |

**数据只放 Vault，是这份契约里唯一的硬线。** 插件不建私有数据库——理由不是审美，是覆盖范围：一旦数据进了私有库，Git 快照撤销不到它、全文检索搜不到它、`forget` 的语义也管不到它。这三样正好是 Ark 全部的可控性来源。所以连插件的调度进度（`scheduler.md`）和通知状态（`notifications.md`）都是插件目录里的普通 Markdown frontmatter，派生缓存删掉后能从这些文件重建。

同一份契约还有四条：

- **能力跨宿主。** 插件的核心操作都要有对应的 MCP 工具。在 QQ 或 Claude Code 里说「加个任务」，调的是同一个工具——界面只是更方便的入口，不是唯一入口。
- **互相独立。** 插件之间不 import、不写对方的数据目录；每个都能单独停用卸载，零插件时 Ark 照常可用。
- **完全信任，不是安全边界。** 进程内插件和 Ark 本身权限相同。只装自己写的或审过代码的插件；`/v1/plugins`、`ark plugins` 与 Obsidian 设置页都带这条提示。
- **不进 Core。** ark-core 不加载插件代码、不理解任务状态，只在 `resume` 时调用宿主给的清单并读插件数据目录里的 `context.md`。

写入也照旧走闸门：插件的 `ctx.vault` 只能读写自己数据目录内的 Markdown，且必须经 ark-core 的 MCP 工具（路径守卫、只读目录、用户手改保护、冲突报告与撤销约束全部生效）；一次插件请求或一次调度运行的写入合并为一个快照，来源记为 `plugin:<name>`。裸写被拒绝。

纪律由 `ark.toml` 的 `[plugins] enabled` 显式名单承担：**发现不等于启用**。启动时扫描仓库 `plugins/` 与 `~/.ark/plugins/`，只加载名单里的，重启生效。在线安装、热加载、更新推送都不做——插件与 Ark 同权限，一个能自动安装插件的机制等于把这份权限开放给网络。

## 三个首批插件

第一个插件用来检验接口够不够，本身就是一次设计评审：

- **任务管理（已交付）**：任务存为 `<data_dir>/tasks/` 下每项一个 Markdown 文件，frontmatter 记 `id`、`title`、`status`（`todo`/`doing`/`done`）、`due_at`、`start_at`、`parent`、`tags`、`created_at`、`completed_at`。当前文件始终权威——手改、撤销、删除都在下一次查询生效；无效记录（无偏移时间、非法状态、重复 ID、父任务缺失或成环）进 `problems` 报告，不猜测不改写。工具面是六个 MCP 工具，外部宿主与自家 Agent 共用。
- **产出工坊（在做）**：每个产出需求一个笔记，写明周期、prompt 或 Skill、输入范围、输出位置与是否发邮件；插件把它们注册成定时任务。每日摘要是第一个模板。
- **采集（在做）**：信息源配置放在 `collect/sources/`，定时轮询采集扩展，结果写进收件箱，在收件箱视图里存档或丢弃。

三者都遵守同一条：**任务状态只是 frontmatter 字段，不是编排。** Ark 没有多 Agent、没有 planner、没有任务状态机——真需要编排的时候再说，不提前造。

## 这套设计的代价

- **状态只能两值**，所以「待复核」「已过期」这类中间态无处安放。代价换来的是一个能脱口而出的答案：这条现在算不算数。
- **`via` 自报**，所以它是追查工具而非防线。真正的防线是「`inferred` 永不进常驻层」这条硬规则，它不依赖任何宿主的自觉。
- **插件同权限**，所以不能自动安装。想装什么得自己往 `ark.toml` 里加一行再重启。
- **不迁 v1 记忆**，所以旧库里的记忆不会自动过来。这是明确取舍：v1 那条链路的账本本身就在被删掉的东西里。
