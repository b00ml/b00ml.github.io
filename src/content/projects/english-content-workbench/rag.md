## 两条入库路径

小文件同步解析；大文件走 OCR 后台，PDF 上限 128MiB、500 页，按校验和去重，成功过的任务直接复用。同步预览默认 3 页上限，因为 OCR 走本机推理，页数一多就卡住进程。

两条路落到同一个中间结构：按顺序排好的块，带文本、类型、警告。坐标按 Python 字符串下标算，不是字节也不是 UTF-16——这点在跨语言传数据时反复坑到我。

## 解析是脏活

Markdown 里一条 `---` 算不算小节标题，要看后面还有没有兄弟标题；表格单元格里的加粗、换行、列表会被摘要吃掉；DOCX 里一个换行不等于一个逻辑段落；PDF 的版面框重叠会裁掉内容。

修完各补了回归用例，但用例是人挑的：它证明这些情况不会退回去，不证明任意一本新教材都解析得对。

## 切分：页是软边界

不按固定字符数硬切。结构布局优先，页只当软边界，跨页的一段话只要有已接受的关系就能合成一块。硬屏障是新章节、缺页、被排除的页、独立题组、表格；表格整行保留，带表头的分页表格会把表头复制到下一页。

leaf 默认 512 字符、重叠 80，parent 2048，只有 leaf 做向量。每个 leaf 带一组 source_segments，记「源文本哪个区间 → leaf 哪个区间」，所以「出自第几页」在多个源段时是一个区间列表，不是页码，段与段之间也不保证连续有序。

## 索引与检索

建索引的顺序：定切块规模和重叠，冻结结构快照，写 leaf 文档和关系，嵌入并按输入哈希校验，最后原子写新索引。失败落在这步，旧索引还能用，但已经花掉的嵌入费用不退；重建保留逻辑文档身份，只有块 id 会变。

检索不只走向量。向量通道走余弦；全文通道照顾英文分词和中文——中文没空格，用 bigram 串做全文检索。两条通道各出最多 30 个候选，按倒数排名融合：得分是各路 1/(60+排名) 之和，再取前 K，默认 5、可选 8。关系通道只在已接受关系上从活动块扩一层。重排默认关着，我试过开，没拿到可重复的收益。

## 取到原文不等于答对

检索包的 complete 字段只说明要的结构材料在预算内送到了，不说明这些材料支撑住了答案。引用同理：可校验的是「引用存在且指向某个块」，不是「这段原文推出了这个答案」。

有个真实例子。问某单元对应哪些题，期望三条落点：向量通道返回了同章节但不含第二条的块，全文通道返回第二条却漏了第一条，融合后前三勉强对，另两条掉出去，最后靠放宽预算捞回来——排序没修，只是预算变大了。

来源回归 44 条全齐备，那是「有对齐源段」意义上的通过，不是专家认可答案，而且只是有限回归。

## 现在的问题

- 知识库小得不像生产：三份资料、81 个 leaf 向量，其中两份只索引了整书的一小部分。
- 排序没修，只扩了预算。token 和延迟一起涨，也不保证下次还灵。
- 表格和公式是弱项。整行保留防得住「一行被劈开」，防不住「原文里这张表本来就没表头」。
- Judge 看不到教材正文，只拿到内容、引用和声明的生成约束。所以「过了检索又过了 Judge」不等于做过基于来源的事实审校。
