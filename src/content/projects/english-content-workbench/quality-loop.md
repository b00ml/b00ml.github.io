## 为什么规则要跑在模型前面

三种内置题型——单选、完形、阅读——各有一张模板，模板版本是 3，输入输出都是 schema，而且都把「有效知识来源」和「人工核验」写成必填。

规则层最先跑：每道选择题恰好四个非空、不重复的选项正文，答案只能是 A/B/C/D 并映射到选项数组的位置，选项正文不带「A.」这类字母标签；完形的 blanks 非空，index 从 1 起按序连续且不重复，passage 里的 `____` 数量必须和 blanks 对得上；数量字段是篇数，不是空数。

这些判断不用读语义，代码直接就能拒绝，所以它们排在模型调用之前：确定性错误不该花一次 token 去问。跨字段规则由配置声明——根对象、小题数组、选项、答案、索引、空格字段都在配置里指明，判断不靠题型名字硬编码，规则跟着配置走。

## 结构校验：JSON 模式加两层校验

输出走 JSON 模式，不是约束解码。模型能保证「给一个 JSON 对象」，不能保证「这个字段只能是 A/B/C/D」，结构得自己兜。顺序是固定的：按 output_schema 生成动态 Pydantic 模型 → 按 JSON 模式调用 → 解析，对有限包装形态展平 → 先过原始 JSON Schema，拒绝那些会被类型转换掩盖的非法输出 → 再过 Pydantic → 执行配置驱动的跨字段规则 → 失败带着具体校验信息重试 → 达到 max_retry 抛明确异常。

原始 JSON Schema 这一层不能省：Pydantic 的嵌套边界可以放宽成动态类型，完整 Schema 才是兜底的那一层。

## 模型判什么，分数怎么算

规则层判不了的交给 Judge：语感、干扰项质量、解析够不够用、难度是否贴合。输出是一组维度分，必须维度完整、ID 唯一、是 0 到 100 的有限数值，缺维度不许悄悄删掉再归一化；每轮最多 3 次尝试，两轮都必须拿到有效结果。

算分分两步：各维度先跨有效采样轮取均值，再按权重加权，总分 = sum(d_i × w_i) / sum(w_i)；过线条件是这一轮 completed，且分数不低于该轮快照里的 threshold。两个维度均分 80 和 90、权重 0.4 和 0.6，算出来 86。默认阈值 70，生效权重和阈值可以被校准覆盖；通过率按每条事件自己的 threshold 统计，不拿一个全局 70 去倒推历史。

分数在这里的角色是筛选器，不是判据：它决定这一稿是进人工，还是带着错误信息回炉改版。改版由 max_revise 封顶，耗尽的进 reject，不会无界重生成。

## 人判什么，凭什么能判

人只看机器判不了的那部分：答案对不对、是否唯一、解析和答案有没有矛盾、引用是否真的支撑这条规则。为了让这一步不变成「凭印象点头」，通过要走一遍确定性校验——按现役模板重新跑 content_guard，历史高分和旧稿都不豁免；要求来源核验的题型，pass 还必须带 reference_verified 和 citations，复核人和引用快照一起写进 provenance。

分数的存法也按这个分工：内容表的 qc_score 是当前展示分，人工通过记 100、驳回记 0，模型原分留在 auto 的 QualityRecord 和每轮的 QualityEvaluation 里。两张表分开，是因为自动首过率要拿 revision 0 的事件当分母，最终通过率拿已 finalize 的事件；只统计留在内容表里的高分稿，会把失败和改版一起丢掉。

## 这套判定换来了什么

发布只认 passed，而且要按现役模板再跑一次确定性校验；样本池只收 passed 和 published 的内容，按条目 id 幂等，同一条重复存不新增记录。few-shot 只取已核验的整例，最多 2 个、额外 8192 字符封顶；示例不当 RAG 事实用，新输出逐字复制样本会被拒绝。

落到证据上：6 条真实内容（单选、完形、阅读各 2 条）跑完自动质检，得分 87.70～91.75，全部落进待人工复核队列。这就是三层拆分换来的东西——机器负责把确定的错和明显不合格的挡在前面，人只对语义负责。
