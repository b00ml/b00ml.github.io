## 数据落在哪，为什么这么落

六种运行状态，各有用处：

| 存什么 | 存在哪 | 用来干什么 |
| --- | --- | --- |
| 任务 | 单节点 SQLite 的任务表 | 进度、错误、取消 |
| M2 审核状态 | 一个 JSON 文件 | 单据结论、AI 结果、回写标记 |
| workflow run | 另一张 SQLite 表 | claim 和 run 的映射、人工状态、revision |
| checkpoint | SQLite | interrupt 前后的图状态 |
| artifact | 按类型和 job 分目录的 rN.json | M3、M4 的版本化结果 |
| 报告和 OCR 缓存 | output 目录 | 失败清单、票面字段复用 |

JSON 状态那个文件用临时文件加 fsync 再原子替换，外层加文件锁。artifact 带 artifactId、revision、schemaVersion、创建时间和 SHA-256，新 revision 不覆盖旧的。

原因很实际：财务结论要能复现。三个月后有人问「这单当时为什么判 FLAG」，我得能拿出当时那份证据，而不是重跑一遍得到另一个答案。output 是运行目录，不当源码提交。

## 异步任务：单节点，也承认它单节点

M2 批量审核、M3 的 AI 复核和 AI 全量巡检走同一套任务队列。请求先返回 jobId，worker 从 SQLite 领 queued 状态的 job，逐阶段更新进度、结果和错误，前端轮询状态接口。取消是协作式的——外部调用跑完，才在安全边界停下。

崩溃语义很简单：服务重启后普通 job 直接标失败，需要重新提交。没有 lease 接管，没有自动重试，没有分布式队列。

为什么不引 MQ：引入它要连带解决重复投递、消费幂等和顺序问题，这些在单机 SQLite 上本来就免了。这个 POC 要验证的是链路能不能给出可审计的结论，不是吞吐。

但有一处不能省。带人工 gate 的 workflow 必须能恢复，所以它单独有 checkpoint 和 revision，不跟普通 job 一个待遇。

## 缓存和两处降级

OCR 按引擎缓存成功结果，重复运行直接复用；解析失败只记录失败信息和统计，不会让整批退出。

制度检索有两条路径。keyword 是默认的，按关键词打分；hybrid 用本地 bge-small-zh-v1.5 做向量召回，再和关键词召回做 RRF 融合，模型不可用时回退到 keyword。

50 条标注集上的 Recall@8：keyword 是 0.78，hybrid 是 1.00。延迟我没写成固定值——它取决于 CPU、首次模型加载和缓存状态，写成一个数就是骗人。

## 测了什么

分层是：单测（规则、契约、工具、grounding、workflow、任务、artifact、M4）、API 契约测试（OpenAPI 路由和错误模型）、检索评测、32 条困难集门禁、注入评测、Prompt 回归（固定输入对 golden 输出结构）、前端测试。CI 里跑 Ruff、pytest、前端构建和离线评测门禁。

数字和它们的口径：

| 数字 | 口径 |
| --- | --- |
| 公开 30 单 M2 F1 = 1.0 | 项目资料口径，不是盲测 |
| 困难集 32 单准确率 1.0000 | 离线合成集，我参与设计的 |
| 注入和结构约束 9/9 | 规则和编排检查，不代表真实攻击全集 |
| 23,461 张台账 → 42 组重复 + 135 项问题 | 42 是组数不是张数，135 是项数，分母不同 |
| 315 笔流水匹配 201 笔 | 63.8% 是笔数匹配率，不是金额匹配率 |
| 一次调查 2 步、8 次调用、14,602 tokens | 单次记录，不代表平均成本 |

还有一句得写清楚：「30 单 2 到 3 分钟」是批量初审的观察值，不含人工终审，不是 SLA。

## 明确不承诺什么

真实运行态没验过。这份快照里没有启动 Docker、真实 ERP、真实 OCR 和真实 LLM。需要真实环境的脚本是有的——端到端评测、Agent 图的冒烟、UI 的 E2E——但它们要 ERP、要 API Key、要服务在跑。

生产安全没做。没有身份认证、RBAC、多租户隔离和托管密钥；前端 POC 还可能把 ERP Key 写进 localStorage。发票影像默认走本地 PaddleOCR，图像不出域；一旦开云端 OCR 或模型复核，单据文本和 OCR 字段就会出域，必须显式开启并申报。

高可用没有。单节点 worker，没有分布式队列、lease 接管和跨实例调度。

还有一条容易含混：系统能回写审核意见，不等于能放行。审核意见和 ERP 审批状态是两件事，后者只有人能改。

## 下一步

后端凭据托管和用户权限、M2 状态接口对齐（前端还在请求一个已经不存在的路由，静默降级了）、300 单规模下的端到端性能与失败基线、人工裁决真值的积累、可多副本运行的 job 和 workflow 存储。

顺序是有理由的：前两个不定，后面所有数字都不可信。
