## M2 差旅审核：先把单子拆成可判的字段

流程是这样：读 PENDING 单据 → 拉审批记录、附件、票据台账 → 本地 OCR 并缓存 → 建发票代码加号码的索引 → 规则跑 11 类 → 可选模型复核 → 分歧转 FLAG → 回写审核意见。

「发票代码加号码的索引」是这条链路里我最满意的一处。OCR 之后把每张票的代码和号码拼成键，同一张票如果在两张报销单上出现，键就撞了，重复发票规则直接命中；台账里再记一次使用次数，第三张也拦得住。这是确定性检查，不依赖相似度。

最难的不是规则，是证据不齐。附件下载失败、OCR 解析失败、城市不在标准表里，这三种情况都不能猜，只能进人工关注。规则写得再全，证据没有就什么都不能说。

## M3 发票稽核：规则扫全量，AI 只出疑似清单

M3 的输入已经是结构化的台账和票面数据，不依赖 OCR，所以它是三条里最确定的一条。

规则扫描做全量兜底：重复票、抬头、税号、税率、连号、供应商档案。这六类跑完存一份 artifact，带 revision，新的不覆盖旧的。

AI 在这一层有两种用法。逐条复核，每条给 CONFIRM、DOUBT、FALSE_ALARM 三选一；分批全量巡检，只产生疑似清单，供人下钻。两种都不改变发票或报销的状态。

这三个取值是刻意的：里面没有「通过」这个选项。模型能做的是把疑点指出来，不是把票放过去。

## M4 银行对账：一对一才是例外

流程：解析银行流水 CSV（编码、表头、金额、重复流水号）→ 拉 OPEN 和 OVERDUE 的应收 → 名称匹配（全称、别名、归一化）→ 金额匹配 → 剩下的按原因聚合成 unidentified。

名称匹配好写。难的是金额：一笔流水可能正好等于一张票，可能是部分付款，也可能一次付清好几张。所以金额这一级分四档——精确、带容差、唯一的部分付款、一笔多票的组合。

组合匹配是唯一会爆炸的地方。一笔款对应 N 张发票，子集数量随 N 指数长，所以我给候选数、组合数、组合搜索时间都设了预算，超了不硬算，交人认领。

自动确认的条件只有一个：候选唯一，且金额条件满足。多候选、没有头款、金额对不上、流水号重复，全部进 unidentified，按原因归类。人不看「匹配了哪些」，只看「哪些没匹配上」。

用一份 315 笔的样例流水跑下来，201 笔匹配上，63.8%。这是笔数匹配率，不是金额匹配率，也不代表对账做完了——剩下那 114 笔才是真正要花时间的地方。

## 哪条最难

按难度排，我的答案是：对账最难，其次差旅，最后发票。

差旅难在证据，规则本身不难写。发票难在维护——供应商档案、连号这些要跟着业务变，但逻辑是确定的。对账难在匹配本身是组合问题，而且没有「正确答案」可以枚举：一笔流水对不上，可能是客户少付，可能是拆单，也可能只是附言没写。

这也是我唯一不敢说跑通的一条。63.8% 意味着三分之一要人接手，而人接手的那部分恰恰是最难的。

三条链路有一个共同点：都停在给意见。没有一条会自动改 ERP 里的单据状态。

## 卡点

M2 和 M3 只对接过合成的 fixture，没有在真实 ERP 上跑过；M4 用的 CSV 是样例格式，真实导出里的脏数据——混合编码、重复表头、金额带千分位或用括号表示负数——覆盖得不够。

下一步我打算挑一批真实导出的流水和单据，先把解析层的失败率统计出来。现在的失败是静默进 unidentified，看不出是规则没覆盖，还是数据根本没读进来。
