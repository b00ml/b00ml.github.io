这条链路有四个判定位置：规则判、OCR 取证、模型提异议、人放行。每一层都有一条不能越过的线，这一页写的是那条线本身，以及把它写进代码之后换来了什么。

## 规则能写到哪一步

差旅这边是 11 类检查：住宿、伙食、市内交通、长途舱位、抬头、税号、金额、重复发票、加班打车审批、缺附件、科目归集。每一条都能说成「取哪几个字段、和哪个标准比、超了报哪个违规码」。

写不进规则的是取不到判据的那部分。OCR 拿不到票面、附件不可用、城市不在标准表、证据不足，这几种情况不兜底成默认值，直接进人工关注——这是规则内部的标黄。OCR 的职责是把票面证据取回来：金额、抬头、税号、票号、日期落到字段，规则优先用这些字段；取不回来，就交给下一层。

分界线很土：字段可枚举、比较关系确定的，写规则；说不清的，不进规则，交给人。11 类全量跑一遍换来的是基线——每张单子都被同一套判据看过，不是抽样看几张。

## 模型为什么只能当第二意见

财务规则要确定性和可回归，所以规则引擎做全量基线，LLM 只作第二意见。它的动作只有一个：独立跑一遍，和规则结论比对。一致，什么都不做；不一致，转 FLAG，由人裁决。

代码里两处硬实现。裁决节点拿到 suggest_approve、suggest_reject 不直接放行或驳回；如果当前结论不是 FLAG，会防御性升级成 FLAG，maintain_rules 则保持规则意见。模型复核调用失败，回退到规则结论，不因为模型没说话就默认通过。

模型没有推翻规则的权力，只有让单子变黄的能力。换来的是一条稳定分工：规则把能写成判断的条款跑完，模型找它没想到的，分歧本身就是要看的东西。

## 标黄不是异常，是产物

FLAG 表示需要人工关注。它和 APPROVE、REJECT 一样是审核意见，不等同于 ERP 的最终审批状态。

进 FLAG 的路径有好几条：规则和模型分歧、证据不足、OCR 失败、城市不在标准表、无法安全匹配、调查工具超时或预算耗尽。

| 情况 | 系统怎么做 |
| --- | --- |
| 规则命中且有票面证据 | 给结论，前端展示理由、违规码和证据字段 |
| 规则未覆盖、票面完整 | 模型独立复核，一致不动，不一致转 FLAG |
| 证据落不了地 | 该条证据标记失败，非 support_flag 结论降级为存疑 |
| 调查失败或预算耗尽 | 生成降级报告，向人工关注方向降级，不中断批处理 |

关键在最后一行：不管中间跑了多少步、调了多少次工具，结论只会往人工关注的方向收敛。这是防「多跑几步就变回通过」的那条线。

## 证据落不了地，结论就得降

每条调查证据带三样东西：call_id、来源 ID、字段路径。校验三件事：工具调用真实存在且成功、来源 ID 出现在那次调用的返回里、字段路径能走到底。

对不上就标记失败。结论依赖它、而它又不是 support_flag 这一类，结论降级为存疑。

一次真实冒烟里，模型给了 6 条证据，4 条通过来源回溯，2 条被 grounding 拦下。换来的是一件事：每条留下来的证据都能回答「它是从哪次调用的哪个字段里来的」。

grounding 做的是来源和字段绑定加启发式回溯，不是语义正确性证明，也不判断制度条款是否适用于具体业务事实。

## 人工 gate 与放行

开了图模式（M2_PIPELINE=graph）和人工 gate（AGENT_HUMAN_GATE=1）之后，interrupt 会暂停并保存 checkpoint；前端从 /api/m2/pending-human 取待审记录，人提交决定时带 expectedRevision，对不上返回 409，重复提交不会互相覆盖。

调查 Agent 的工具注册表注册 5 个只读工具：query_travel_standards、search_policy_kb、get_approval_records、get_invoice_ocr、check_invoice_ledger，每个声明 readonly、JSON Schema、超时和输出大小上限。预算也是可数的：默认 5 步、工具调用上限 2×max_steps+4、token 30,000、墙钟 90 秒，超了往人工关注方向降级。

注册表里没有任何 ERP 状态变更接口——权限边界不靠提示词自觉，靠接口不存在。系统能回写审核意见，不等于能放行；ERP 里的审批状态从头到尾只有人能改。另两段在[三条链路，三种难度](/projects/finance-review-agent/workflows)和[每个数字的口径](/projects/finance-review-agent/engineering)。
