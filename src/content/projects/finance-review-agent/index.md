## 它能完整办成的一件事

ERP 里的一张待审单据进来，走完一条链：拉附件、本地 OCR 把票面金额、抬头、税号、票号、日期落到字段、规则把能写成判断的条款全量跑一遍、模型独立给一次第二意见、规则和模型不一致的标黄、审核意见回写到单据上。

审核员看到的不是「通过」或「驳回」，是「这里可能有问题，依据是这条」。ERP 里的审批状态从头到尾只有人能改——调查 Agent 的工具注册表里没有任何一个写接口。

## 我为什么把它做成这样

**宁可标黄也不猜。** 规则和模型不一致，转 FLAG；证据不足、OCR 失败、城市不在标准表，也转 FLAG。FLAG 不是异常状态，是正常产物。裁决节点只允许把结论往人工关注的方向推，不往回走。

**证据链优先于准确率。** 每条调查证据绑定 call_id、来源 ID 和字段路径，落不了地就判失败、结论降级为存疑。宁可少一条证据，也不留一条说不清出处的。

**不做端到端黑箱。** 给审核员的是一个具体疑点和它的依据，不是一个结论。全信模型他要担责，全不信等于重做；只有落到具体疑点，那一步才算真省下来。

## 三条链路

- [机器判得清，人才敢放行](/projects/finance-review-agent/boundaries)：规则、OCR、模型、人四层各管什么，最后一列写死「明确不能做什么」。
- [三条链路，三种难度](/projects/finance-review-agent/workflows)：差旅难在证据，发票难在规则维护，对账难在匹配本身。
- [每个数字的口径](/projects/finance-review-agent/engineering)：状态落在哪、任务怎么流转、缓存和降级怎么设计，以及每个数字是怎么算出来的。

## 做到什么程度

三条链路各有产物。差旅是最完整的一条：读 PENDING 单、拉附件、本地 OCR、规则跑 11 类检查、可选模型复核、分歧转 FLAG、回写审核意见，图模式下还能开调查 Agent 和人工 gate。发票稽核是规则扫全量兜底，重复票、抬头、税号、税率、连号、供应商档案六类，AI 只输出 CONFIRM、DOUBT、FALSE_ALARM 三种意见，全量巡检只产疑似清单。银行对账做金额四级匹配加组合搜索，超预算交人认领。

规模是拿真实台账跑出来的：23,461 张发票，扫出 42 组重复票和 135 项票面问题；315 笔银行流水匹配上 201 笔。这些数字的分母和适用范围逐个列在子页里。

工程上前端、API、规则、OCR、检索、Agent 图、任务队列、对账都在，单测、API 契约、离线评测和前端构建都在 CI 里跑。真实模型的冒烟也跑通过一次：2 步、8 次工具调用、14,602 tokens，6 条证据里 4 条通过来源回溯。

## 适用范围

一家制造企业的财务审核 POC，三条业务链路、单人跑真实台账与合成数据。身份认证、RBAC、多租户、消息队列与高可用 worker 不在这一版范围内——它们解决的是「给十个财务同时用」，不是「机器能不能给出可审计的审核意见」。
