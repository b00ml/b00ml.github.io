> 低代码是探路的好工具，但它不是生产线。这篇讲的是我怎么在同一个场景上连撞三次墙，然后认清那条"必须自己造"的边界线到底划在哪里。

<div class="callout"><span class="lbl">TL;DR</span><p>低代码把"能跑通"的成本压到很低，代价是它替你决定了三件事：<span class="mark">校验发生在客户端、质量只能靠人看、失败之后没有状态可恢复。</span>这三件事恰好都不是配置项，而是架构项。所以当一个内容生产流程要按天稳定出量时，问题就不再是"能不能搭出来"，而是"错了之后谁负责、从哪儿接着跑"。</p></div>

## 01 · 先说清楚：低代码没让我失望，是我用错了它

原文的场合我保持匿名：**早期在业务场景里，我用低代码拖拽搭过一版出题链路**——把几个节点连起来，输入知识点、输出题目，中间挂一个模型调用，再挂一个条件分支做简单的字段判断。两个小时就有一条能演示的流水线，这件事本身是低代码最大的价值，我不想否认它。

问题是它从"能演示"走到"每天稳定出量"的那几步，每一步都撞在同一类东西上。我把这三次撞墙按发生顺序写下来，因为它们各自指向不同的机制。

## 02 · 第一次撞墙：校验在客户端，等于没有校验

低代码平台的校验能力是给表单用的。它能做"这个字段必填""这个数字在 1 到 100 之间"，这些对输入表单足够，对模型输出不够。

具体的失败是这样的：一道选择题要求恰好四个非空且不重复的选项、答案只能是 A/B/C/D 并且映射到选项数组的位置、选项正文里不能带"A."这类字母标签。低代码里能做的检查是"字段存在"和"字段是数组"；再往下的跨字段约束——答案 ID 要能落到选项数组的索引上、完形填空的 `____` 数量必须和 blanks 数组长度对得上——它没有地方放。

于是这些判断被塞进了两处：一是客户端的表单校验，二是人工的眼。客户端校验的问题是它拦不住任何不是从那个表单进来的东西（重跑、批量、接口调用全都绕过），人工的眼的问题是它每天只能看几十条。

这条撞墙给出的结论很直接：**校验必须是服务端的，而且必须在调用模型之前跑。**确定性错误不该花一次 token 去问模型——判"选项里有没有重复"不需要语义能力，只需要一段代码。

后来这一层在自研版本里落成了固定的顺序：按输出 schema 生成动态的 Pydantic 模型 → 按 JSON 模式调用 → 解析 → 先过原始 JSON Schema → 再过 Pydantic → 再执行配置驱动的跨字段规则 → 失败带着具体校验信息重试 → 达到上限抛明确异常。

其中"先过原始 JSON Schema"这一层当初差点被我省掉，理由是"Pydantic 也会校验类型"。不能省：Pydantic 的嵌套边界可以放宽成动态类型，那些被类型转换悄悄掩盖过去的非法输出，只有完整 Schema 才兜得住。

## 03 · 第二次撞墙：质量靠抽检，等于没有质量

第二处更贵。低代码里判断模型输出好不好，只有一条路——人看。

人看的根本问题不是慢，是**不可累积**。今天张三觉得这道题还行、李四觉得干扰项太弱，两条判断都不会留下来；同一道题下周重跑一遍，还是靠人重新看一遍。三个星期之后你对"这批内容质量如何"的全部答案，仍然是一句"我抽了二十条，感觉还可以"。

自研版本里这一层被拆成了三段判定，各管一段：

1. **规则先跑**，拒掉所有能确定性判断的错——上面那一堆跨字段约束。
2. **模型给一个可比的分数**，按维度加权：语感、干扰项质量、解析够不够用、难度是否贴合。总分 = 各维度均分按权重加权，默认阈值 70。
3. **人只收机器判不了的那部分**：答案对不对、是否唯一、解析和答案有没有矛盾、引用是否真的支撑这条规则。

这里有两个设计决定值得单独讲。

**分数是筛选器，不是判据。**它决定这一稿是进人工，还是带着错误信息回炉改版；它不决定这稿能不能发。低于阈值就自动进下一轮改版（最多 N 轮，耗尽进 reject），达到阈值就停在"待人工复核"等一个人按通过或驳回——绝不自动入库。这个拆分让通过率有了两种口径：自动首过率拿第一轮事件当分母，最终通过率拿已定稿事件当分母。混成一个数就会把"改版救回来的"和"一次就对的"算成同一件事。

**权重和阈值可以被校准覆盖，但校准要有门槛。**真实的校准信号不是"机器打分高不高"，而是"机器打了高分、人却驳回了"这种分歧样本（假通过）。累计够量、并且其中假通过样本够数，才允许反向调整维度权重——门槛没到之前，显示的必须是"冷启动保护中"，而不是一个看起来已经调好的权重表。

## 04 · 第三次撞墙：中断之后无法续跑，等于没有流水线

第三次撞墙最不像技术问题，但它是三条里最致命的。

低代码的执行是一次性的。链路跑到第七个节点挂了，你能看到的是一条失败记录，看不到"它跑到哪儿了""前面那几个模型的调用白花了吗""重跑一遍会不会把已经入库的那几条又来一遍"。

在演示里这无所谓——重跑一遍两分钟。在按天出量的场景里，这意味着任何一次网络抖动、任何一次上游限流，都会把整批打回起点。而模型调用是有成本的，重跑不是免费的。

自研版本里这一层要解决的是"一次生成跨越五个地方，没有任何一个事务盖得住"：已接收的请求在数据库、待执行的条目在队列、进行中的图在检查点、OCR 成功的页在文件卷、已经发生的调用和费用在 Trace。目标是四句话：有限重试、可追溯、可补偿、尽量不重复。

具体靠两个机制落地。

**Outbox 加条件租约。**请求进来时，任务行和 Outbox 行在同一个数据库事务里写入，事件号唯一。之后 relay 读最早一条 pending、置为 sending、attempts 加一、提交，再拿稳定的那个事件号去投递；成功写 sent，失败回 pending 并按退避重排，次数耗尽进 dead。领取用 `skip locked` 加带随机令牌的 CAS——**令牌决定谁能 ack**，这样重复投递不会变成重复执行。这是"要发"和"已发"必须分成两行的理由：合成一行时，你可能在一个已经发出去的请求上再发一次，也可能在一个没发出去的请求上标记已发。

**检查点续跑。**图的状态按 thread 持久化。重跑时先看这个 thread 有没有最终状态：有就直接返回；停在人工 interrupt 上就停在待复核；其余从保存的节点接着跑。幂等靠三层身份——(任务 ID, 条目序号) 唯一、thread ID 唯一、内容表 thread 非空唯一。

还有一条规则比"多恢复几条"更重要：**已完成、已取消、待复核这些终态不自动复活。**恢复逻辑天然倾向于多救一点，但把一个人已经决定驳回的东西自动拉回来重跑，比丢掉几条更糟。

## 05 · 选型边界：什么时候该自己拥有状态机

把三次撞墙放在一起看，它们指向同一个东西：低代码替你决定了**控制流放在哪里**。而上面三个机制——服务端校验、多轮改版与硬阈值、跨进程一致性与断点续跑——全部都是控制流。

注意这四条里**没有"模型不够好"**。这是我早期最容易搞错的判断：把问题归到模型能力上，然后换一个更贵的模型，撞墙照旧。三次撞墙没有一次是模型能力不足造成的——选项重复不是模型不会数，是没有代码去数；质量不可累积不是模型不稳定，是判断没被记下来；无法续跑更不是模型的事。

## 06 · 反过来说：什么时候低代码是对的

我不打算把这篇写成"自研一定更好"，那是另一种偷懒。

低代码在三种情况下明显更优，而且我不觉得应该绕开它：

- **还没想清楚流程时。**拖一版出来给业务方看，两小时能换来一句真正的问题，比写两周代码强。
- **产出频率低、人工守着跑时。**一周跑三次的东西，为它建一套 Outbox 和租约是过度设计，维护成本永远超过收益。
- **校验规则还没稳定时。**规则一天改三次的阶段，把规则写进代码是负担；这个阶段真正该做的是先把规则收敛成一张能讨论的表。

我自己的做法是**用低代码探路，用自研收敛**，而不是二选一。探路阶段要的是速度和可讨论性，收敛阶段要的是可验证性和可恢复性——这两个阶段的最优解本来就不是同一个东西。

有一条我付出过代价的教训：**不要为了迁就低代码的能力去扭曲流程设计。**我干过一次——因为平台只能做单层条件分支，我把一段本来的顺序判定改成了嵌套判断，结果是它跑得通，但没人能读懂它为什么这么判，包括三周后的我。流程设计一旦为了工具变形，后面每加一条规则都在给这个变形打补丁。

## 07 · 落到一个人维护的项目里

最后说点实际的。这套东西一个人维护，最容易死在"太重"上。

我的取舍是这样的：**机制要全，实现要小。**

Schema 硬拦截是必须的——它省的是真金白银的 token，而且它是最容易写对的一层。多轮 Judge 加硬阈值也是必须的，但轮数可以很小（两三轮就够），因为再往上加的收益衰减得很快。Outbox 和租约是三者里最重的一项；如果只是一次性批处理、没有跨进程，那就退化成"任务表 + 幂等键"，别硬上完整投递语义。检查点是"能不能续跑"的全部答案，它同时也是最便宜的——状态持久化本来就是框架给的。

写这篇的时候我盯了一眼自研版本的证据：1154 个测试通过，其中 1091 个不连真实数据库、63 个连真实 PostgreSQL，应用层覆盖率 84.05%，门槛设在 80%。这些数字不是用来炫耀的，是用来回答"这套东西你敢不敢改"——一个人维护的系统，改动的勇气只能来自测试。

<p class="pull">低代码让你两小时看到效果，自研让你两年后还敢改它。</p>
