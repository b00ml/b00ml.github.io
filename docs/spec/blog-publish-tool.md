# 博客发布工具：入库与发布

> 待发布底稿。issue tracker 配置好之后，这份内容作为 issue 发出；届时本文件改为一条指针或删除。

## Problem Statement

我的文章先在 Obsidian 里写。要让它上线，现在得手工走一遍：把源笔记复制进仓库、把 `![[...]]` 换成标准图片语法、删掉正文里那个和标题重复的 H1、自己想一个英文 slug、写 description 和标签、把图片从 Obsidian 的附件目录搬到仓库并改名、然后构建、提交、推送、等 GitHub Actions、最后自己去线上确认页面真的打开了。

这套流程有十几步，其中两三步每次都要做判断，其余全是机械动作。但机械动作里有几个会**静默失败**的坑：图片放在 `src/content/**` 之外会让 RSS 构建直接崩掉；忘了删正文 H1 会让页面出现两个 h1，伤 SEO 也伤目录；标签随手起名字，半年后会长出几十个近义标签，而每个标签都是一个公开可索引的页面，删就是 404。

手做一次十几分钟，一个月写两篇就够烦。更麻烦的是它让我在「想写」和「写完」之间多了一段不想干的事。

## Solution

两个命令，默认都只打印「计划」，加 `--apply` 才动手。

`ingest` 把一篇源笔记变成仓库里的一篇文章：转换方言、搬图并校验哈希、生成 slug 与字段、打印计划（含正文 diff 和告警）。`publish` 把工作区里的改动构建、提交、推送、等部署完成、验证线上真的能打开。

判断由我做（或由 agent 提出来让我确认），机械动作交给脚本。我不需要记住那十几个坑，也不会因为偷懒跳过一次而静默上线一篇坏文章。

## User Stories

1. 作为博主，我想给工具一个源笔记的路径就能看到「这篇文章会变成什么样」，这样我在动任何文件之前就知道结果。
2. 作为博主，我想在计划里看到工具为 title、description、tags、pubDate 各取了什么值，以及**每个值是从哪来的**，这样我不用怀疑它是不是瞎猜的。
3. 作为博主，我想在计划里看到图片从哪搬到哪、多少字节、哈希对不对，这样搬图这一步不再是我要操心的事。
4. 作为博主，我想在更新一篇已有文章时看到**正文的 diff**，这样我不会在不知情的情况下覆盖掉自己在仓库里手改过的东西。
5. 作为博主，我想只有一次确认机会，确认完就一路跑到线上，这样我不用盯着每一步。
6. 作为博主，我想在计划里看到告警（外站图片、缺 description、标签不在词表里、没有 H1、H1 与标题措辞不同），这样我能在落盘前决定要不要改。
7. 作为博主，我想让工具只从站内已有的标签里挑，新增标签必须我明确同意，这样标签不会长成几十个近义词。
8. 作为博主，我想让工具要求运行前工作区是干净的，这样失败时它能确切地把我带回原点。
9. 作为博主，我想让工具在失败时精确回滚它自己碰过的文件，这样一次失败的尝试不会留下半成品。
10. 作为博主，我想让 `publish` 拒绝在工作区里有无关改动时运行，这样它不会顺手提交我还没想好的东西。
11. 作为博主，我想让 `publish` 在推送后真的等到线上可用，这样「完成」对我意味着页面能打开，而不是「命令没报错」。
12. 作为博主，我想让部署偶发卡住时自动重试一次，这样偶发的平台抖动不需要我介入。
13. 作为博主，我想让工具在源文件于 dry-run 与 apply 之间被改动时中止，这样我确认的和执行的是同一个东西。
14. 作为博主，我想让提交信息自动生成成符合仓库规范的形式并在计划里出现，这样我不必现想。
15. 作为博主，我想让正文里与标题重复的 H1 被删掉，这样页面只有一个 h1。
16. 作为博主，我想让措辞不同的正文 H1 被删掉但保留下来当作 description 的草稿，这样那条更完整的一句话标题不会白丢。
17. 作为博主，我想让没有 frontmatter 的源笔记也能入库（从正文 H1 或文件名取标题，日期缺失就用今天），这样 101/138 篇没有 frontmatter 的笔记不会被挡在门外。
18. 作为博主，我想让工具把 remote 图片原样保留、只搬运本地附件，这样入库不会因为别人的 CDN 有防盗链而失败。
19. 作为博主，我想在图片指向**别人站点**时收到告警，这样我不会在没意识到的情况下引用别人的版权内容。
20. 作为博主，我想让 `ingest` 和 `publish` 能分别单独执行，这样改一个错字时我只需要跑发布。
21. 作为 agent，我想让命令在 stdout 上输出结构化的计划、以退出码表达成功与失败，这样我不需要解析人类可读的日志。
22. 作为 agent，我想让 CLI 在任何需要判断的地方停下来而不是猜，这样我不会被迫接受一个我没法解释的结果。
23. 作为 agent，我想有一份自包含的说明写清楚前置条件、两条命令、字段怎么定、以及已知失败模式，这样我不需要从源码反推用法。
24. 作为未来的贡献者，我想读到为什么这个工具被拆成「模型判断 + 脚本执行」两半，这样我不会试图把字段生成塞进 CLI。
25. 作为未来的贡献者，我想让测试只打在一个边界上（`ingest --dry-run` 的输出），这样重构内部模块不会让测试大面积变红。
26. 作为未来的贡献者，我想让计划里的字段来源、告警代码是稳定的词汇，这样我可以放心地在其上写断言。

## Implementation Decisions

**拆成两个可独立执行的阶段。** 入库（源笔记 → 工作区改动）与发布（工作区改动 → 线上页面）是两条命令。入库含判断，发布不含判断。两者各自支持「只打印计划」与「执行」两种模式，执行必须显式加 `--apply`。

**判断归模型，机械归脚本。** 见 `docs/adr/0001-split-judgment-from-mechanics.md`。CLI 不做任何猜测：缺字段就停下要求补，不取默认值兜底。

**代码分区。** 判断核心（方言转换、H1 判定、slug 生成、图片搬运与哈希、标签词表、计划组装）放在与站点源码同源、能被现有测试命令自动发现的目录，从而免费获得类型检查与 lint；命令入口只做参数解析、IO 与退出码。

**集合必须显式给出。** `ingest` 要求 `--collection blog|notes|product`，不做内容自动分类。集合按主题划分。

**元信息取值优先级。** title：正文第一个 H1 → 文件名去扩展名。pubDate：源笔记 frontmatter 的 created → 当天。description：措辞不同的正文 H1 → 源笔记 frontmatter → 缺失（并告警）。

**正文 H1。** 与 title 等价（忽略标点、空白、大小写差异）则删除；不等价也删除，但把文本交给 description 作草稿。

**标签受控。** 允许集合在运行时扫描站内现有文章的 tags 汇总得到，不维护独立白名单文件。计划里区分「已有标签」与「新增标签」，新增必须显式确认。

**图片。** 只处理本地附件：复制进站点图片目录、重命名为不含中文与时间戳的名字、校验 SHA256 一致后记录。remote 图片原样保留；指向第三方站点的图片额外告警。

**工作区前置条件按阶段区分。** `ingest` 要求工作区干净——这样失败时回滚是精确的。`publish` 要求工作区「脏，但只脏在本工具该动的位置」，通过版本控制的变更清单校验，不匹配即中止。

**计划是一份数据结构，也是唯一的对外契约。**

```
Plan = {
  source:  { path, sha256, bytes }
  article: { collection, slug, targetPath, exists }
  fields:  { title, description, tags, pubDate }  // 各自带 value + source
  body:    { h1: { found, text, equivalentToTitle }, diff | preview }
  images:  [ { from, to, bytes, sha256, remote } ]
  warnings: [ { code, message } ]
  commit:  { message }
}
```

`source` 字段来源的取值集合：`h1` / `frontmatter` / `filename` / `today` / `h1-draft` / `missing` / `existing` / `new`。告警代码集合：`remote-image` / `third-party-image` / `missing-description` / `tag-not-in-vocabulary` / `no-h1` / `h1-differs`。这两组词是测试断言的对象，属于对外契约。

**一致性校验。** 计划里携带源文件哈希。`--apply` 时重算；不一致则中止并要求重新 dry-run。

**发布序列。** 校验工作区变更范围 → 构建 → 跑测试 → 用计划里的提交信息提交 → 推送 → 轮询部署状态 → 验证线上文章地址返回 200 → 输出线上地址。部署状态长时间停留时重试一次。提交信息在计划阶段生成并确认，使用仓库既有的提交规范。

**重复入库。** 同一 slug 已存在视为「更新这篇文章」。计划里展示正文差异，确认后覆盖。slug 由 title 派生，因此 title 改变会产生一篇新文章，旧的保留。

## Testing Decisions

**什么算好测试。** 只断言外部行为：给定一份源笔记，命令输出的计划是什么。不断言内部函数名、模块划分、调用顺序。断言的对象是上一节列出的计划结构与两个词汇集合（`source` 取值、告警代码），这样重构内部实现不会让测试变红，而契约一旦变更测试一定会红。

**唯一测试边界。** 入库阶段的命令以只读模式运行，解析其结构化输出。一条边界覆盖五个决策：frontmatter 转换、H1 判定、slug 生成、图片重命名与哈希、标签词表校验。这是「模型依赖的契约」所在的位置，也是最高的可用边界。

**测什么。** 一组 fixture 源笔记，每个对应一类边界情况：完全无 frontmatter 且无 H1、有 H1 且与标题等价、有 H1 且措辞不同、`![[...]]` 本地附件、`![alt](path)` 本地附件、remote 图片、第三方站点图片、标签全部命中词表、标签部分超出词表、文件名含中文与空格、同一 slug 再次入库。每个 fixture 断言计划的关键字段与告警集合。

**不测什么。** 发布阶段不写自动化测试——它依赖真实的版本控制与远端，边界不稳定。它靠手工跑一次完整发布来验证，这一点在 Out of Scope 里说明。

**先例。** 仓库现有的测试都是「代码旁边放同名 `*.test.ts`、用 `bun:test` 断言纯函数」的形式（配置校验、SEO 元数据、RSS 条目、阅读时长）。本规格沿用这个形式与命名习惯，只是断言对象从单个函数变成一条命令的计划输出。

## Out of Scope

- **批量发布。** 只处理一篇。真正的瓶颈是每篇都要判断，批量只会把待判断的东西堆成一堆。
- **本地 Web 界面。** 解决的是当前还不存在的痛点，且成本远高于其他部分。
- **自动发现新笔记（监听目录）。** 触发权留在人手里。
- **草稿管理。** 不做上线/下线切换；`draft` 字段仍由源笔记或人工决定。
- **封面图与自动配图。** 正文图片会自动获得放大效果，但封面字段当前不渲染，不做。
- **内容改写或润色。** 工具只搬运和校验，不创作。一个「顺手帮你润色」的功能会悄悄改掉作者的语气，而那是这个博客唯一的个人资产。
- **发布阶段的自动化测试。** 见上。
- **多个站点复用。** 工具与这个仓库的约定同源演进，不做成通用工具。

## Further Notes

- 术语见 `GLOSSARY.md`：源笔记 / 入库 / 发布 / 文章 / 计划 / 确认点。特别是「上传」这个词不再使用——它同时指代入库和发布，而这正是本规格要拆开的两件事。
- 已知的六个失败模式已写在 `docs/publish-workflow.md`，其中包括图片位置导致 RSS 构建失败、删除文章后构建缓存残留、`![[...]]` 不被渲染等。新工具的存在理由之一就是让作者不必记住它们，但这六个都应当有对应的 fixture 或告警。
- 源笔记的实际分布（138 篇中 101 篇无 frontmatter、119 篇有正文 H1、其中仅 49 篇与标题一致、10 篇含图片且 41/52 个本地附件名带 13 位时间戳后缀）决定了元信息取值优先级与图片命名的设计，不是假设。
